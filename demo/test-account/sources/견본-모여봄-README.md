# 모여봄 — 교내 스터디룸 · 세미나실 예약 서비스

2025년 2학기 캡스톤디자인 (2025-09 ~ 2025-12) · 4명 팀(백엔드 2 · 프론트 1 · 기획/디자인 1)
나는 백엔드 중 **예약 · 결제 없는 확정 흐름과 알림**을 맡았다. 다른 백엔드 팀원은 회원 · 학과 인증과 관리자 페이지를 맡았다.

## 왜 만들었나

학과 사무실이 스터디룸 6곳 예약을 구글 시트로 받았다. 같은 칸에 두 사람이 이름을 쓰는 일이 학기마다 수십 번 있었고, 조교가 매일 아침 시트를 보고 겹친 예약을 전화로 정리했다. 학과 조교님 인터뷰(2025-09-05)에서 "한 주에 3~4건은 겹친다"고 들었다.

## 기술

- Spring Boot 3 · JPA · MySQL 8 · Redis(알림 큐) · React(프론트 담당)
- 배포: 학교 클라우드 VM 1대에 Docker Compose (배포 스크립트는 다른 백엔드 팀원이 작성)

## 내가 한 일

### 1. 같은 시간에 두 예약이 잡히는 문제

- 첫 버전은 "예약 전에 겹치는 예약이 있는지 조회 → 없으면 저장"이었다. 부하 테스트(nGrinder, 가상 사용자 50명이 같은 칸을 동시에 예약)에서 **100번 중 7번** 중복 예약이 생겼다.
- 원인: 조회와 저장 사이에 다른 요청이 끼어든다. 트랜잭션만 걸어서는 MySQL 기본 격리 수준(REPEATABLE READ)에서 막히지 않았다.
- 비관적 락(`SELECT … FOR UPDATE`)과 유니크 제약 두 가지를 비교했다. 예약은 30분 단위 칸이라 `(room_id, slot_start)` 유니크 제약으로 바꾸고, 여러 칸 예약은 칸마다 행을 만들어 한 트랜잭션에서 저장했다. 충돌하면 DB 가 막고, 서버는 409 로 "방금 다른 사람이 예약했어요"를 돌려준다.
- 바꾼 뒤 같은 부하 테스트 1,000번에서 중복 0건. 락을 쓰는 안보다 평균 응답이 약 40% 빨랐다(측정 기록: `docs/load-test-1012.md`).

### 2. 내 예약 목록이 느렸다

- 예약 30건 이상인 계정에서 "내 예약" 화면이 1.8초 걸렸다. 쿼리 로그를 켜 보니 예약마다 방 · 건물을 따로 불러오는 N+1 이 있었다(한 번 열 때 쿼리 61개).
- fetch join 으로 한 번에 불러오고, 지난 예약은 페이지로 나눴다. 0.3초로 줄었다.

### 3. 노쇼 줄이기 — 시작 10분 전 알림

- 학과 요청: 예약해 놓고 안 오는 사람이 많다.
- 예약 시작 10분 전에 카카오 알림톡 대신 학교 메일 + 웹 푸시로 "아직 이용하시나요? 안 쓰면 취소해 주세요" 알림을 보냈다. 알림은 Redis 정렬 집합에 시작 시각으로 넣고 1분마다 꺼내 보냈다.
- 시범 운영 3주(2025-11-10 ~ 11-30) 동안 학과 집계로 노쇼가 주당 평균 11건에서 4건으로 줄었다. 다만 알림을 끈 사람이 많아 정확한 효과인지는 확인하지 못했다.

## 팀으로 한 일

- 매주 화요일 스프린트 계획, 금요일 데모. 기획 팀원이 학과 조교님과 주 1회 만나 요구사항을 받아 왔다.
- 화면 설계와 디자인은 기획/디자인 팀원이, 관리자 통계 페이지는 다른 백엔드 팀원이 만들었다.

## 결과

- 2025-12 캡스톤 발표회 우수상(학과 3팀 중 하나).
- 2026년 1학기부터 학과에서 실제로 쓰는 중(조교님이 운영, 우리는 버그만 고친다).
