# export-api — Markdown 내보내기 · FE → BE (S-33)

- 쓰는 곳: FE 연결 · 내보내기 화면(전체) · 활동 세부(활동 하나) · 지원 화면(지원 하나) — FE#149
- 만드는 곳: BE — BE#118
- SPEC: `R-04` `F-12` / `S-33` · §0 「경험과 자료는 사용자 것이다」 · `S-56`(확인 전 답은 싣지 않는다)

경험은 사용자 것이라 들고 나갈 수 있어야 한다. 내보낸 파일은 사람이 읽고, **다른 AI(ChatGPT · Claude 등)에 붙여 넣어도 뜻이 바뀌지 않게** 출처 상태 · AI 해석 표시를 파일 안에 그대로 싣는다 — MCP(`mcp-api.md` 「읽는 규칙」)와 같은 규칙을 파일로 들고 가는 것이다.

## 흐름

```
FE 버튼 ─GET /api/exports/…──▶ BE: 지금 데이터로 Markdown 한 장을 만들어 바로 돌려줌(저장 안 함 · AI 호출 없음)
FE ◀── 200 text/markdown (Content-Disposition: attachment) ── 파일로 내려받기
FE ◀── 4xx · 5xx JSON(README 「오류 응답」) ──────────── 오류 · 다시 시도
```

- **동기 호출 하나**다. 분석 작업 · 폴링이 없다 — LLM 을 부르지 않고 DB 를 읽어 글로 옮길 뿐이라 빠르다.
- **하루 분석 횟수를 쓰지 않는다**(429 `DAILY_LIMIT_EXCEEDED` 없음). 로그인은 필요하다(401 `UNAUTHENTICATED` — `auth-api.md`).
- 내보낸 파일 · 내보낸 기록은 서버에 남기지 않는다. 같은 데이터면 `exportedAt` 말고는 같은 글이 나온다(BE 는 스냅샷 시험으로 지킨다).

## 정한 것 · 버린 안

| 정한 것 | 이유 | 버린 안 |
| --- | --- | --- |
| BE 가 `text/markdown` 을 만들어 준다 | 출처 상태 · 해석 표시 규칙이 한곳(BE)에 있고, 나중에 MCP · 다른 화면에서도 같은 글을 쓴다 | FE 가 목록 API 를 모아 조합 — 호출이 많고(활동 N 개면 N+1) 규칙이 FE 에 들어간다 |
| 대상마다 **파일 하나**(`.md`) | 받는 쪽 도구(메모장 · 노션 가져오기 · 옵시디언 · 다른 AI 붙여넣기)가 다 바로 연다 | 활동마다 파일을 나눈 `.zip`(노션 · 옵시디언 내보내기 방식) — 압축 · 링크 규칙이 늘어 데모 범위 밖. 「전체」가 커지면 그때 |
| 맨 위에 YAML front matter + 「읽는 법」 | front matter 는 옵시디언 · Jekyll · Hugo 등이 읽는 사실상 표준 머리말이라 기계가 범위 · 시각을 읽는다. 「읽는 법」은 다른 AI 가 상태 표시를 틀리게 읽지 않게 한다 | 머리말 없이 본문만 — 파일만 봐서는 언제 · 무엇을 내보냈는지 모른다 |
| 상태 · 해석은 **글자 꼬리표**(`[원문 확인]` · `(AI 해석)`)로 | 아이콘 · 색은 Markdown 밖에서 사라진다. 글자는 어디에 붙여도 남는다 | 이모지(✅ · ⚠) — 뜻이 읽는 사람 · AI 마다 다르게 읽힌다 |
| 「전체」는 **활동 · 경험**만. 지원은 지원 하나씩 | SPEC S-33 「활동 · 경험을 꺼낸다」. 지원은 문항 · 답 · 추천이 붙어 길다 | 전체에 지원까지 — 파일이 길어지고 경험이 추천마다 되풀이된다 |

## 엔드포인트

| 대상 | 호출 | 없는 대상 |
| --- | --- | --- |
| 전체 | `GET /api/exports/all` | — (빈 계정도 200) |
| 활동 하나 | `GET /api/exports/activities/{activityId}` | 404 `ACTIVITY_NOT_FOUND` |
| 지원 하나 | `GET /api/exports/applications/{applicationId}` | 404 `APPLICATION_NOT_FOUND` |

요청 본문 · 쿼리 없음.

응답 200

| 헤더 | 값 |
| --- | --- |
| `Content-Type` | `text/markdown; charset=UTF-8` (RFC 7763) |
| `Content-Disposition` | `attachment; filename="<ASCII 이름>"; filename*=UTF-8''<퍼센트 인코딩한 한글 이름>` (RFC 6266 · RFC 8187) — 아래 「파일 이름」 |
| `Access-Control-Expose-Headers` | `Content-Disposition` — 교차 출처(`app-` → `api-`) `fetch` 에서 FE 가 파일 이름을 읽으려면 필요하다(CORS 기본 노출 헤더가 아니다) |
| `Cache-Control` | `no-store` — 개인 데이터라 중간에 남기지 않는다 |

- 본문은 UTF-8 · **BOM 없음**(BOM 이 있으면 front matter 를 못 읽는 도구가 있다) · 줄바꿈 `\n`.
- 오류는 JSON 이다(README 「오류 응답」) — `Content-Type: application/json`. FE 는 `response.ok` 로 가른다.
- 401 `UNAUTHENTICATED` · 404(위 표) · 500 `INTERNAL_ERROR`.

### 파일 이름

`차곡-<대상>-<이름>-<YYYYMMDD>.md` — 날짜는 서울 시간 내보낸 날.

| 대상 | `filename*`(한글) | `filename`(ASCII 대체) |
| --- | --- | --- |
| 전체 | `차곡-전체-20261111.md` | `chagok-all-20261111.md` |
| 활동 | `차곡-활동-바꿔요 — 캠퍼스 중고거래 앱-20261111.md` | `chagok-activity-7-20261111.md` |
| 지원 | `차곡-지원-OO 백엔드 부트캠프-20261111.md` (지원처 이름이 없으면 `차곡-지원-21-…`) | `chagok-application-21-20261111.md` |

- `<이름>` 다듬기: 파일 이름에 못 쓰는 글자(`\ / : * ? " < > |` · 제어 문자)는 빼고, 공백 여럿은 하나로, 앞뒤 공백 · 점은 뺀다. 40자가 넘으면 40자에서 자른다. 다듬고 남은 게 없으면 ID.
- FE 가 헤더를 못 읽으면(목 모드 등) ASCII 이름 규칙으로 스스로 짓는다.

## 문서 모양

### 공통 머리

```markdown
---
exportedFrom: 차곡 — 내가 우왕이 될 상인가
scope: activity
id: 7
exportedAt: 2026-11-11T21:00:00+09:00
---

# 바꿔요 — 캠퍼스 중고거래 앱

> **읽는 법** — 이 파일은 사용자가 차곡에 쌓은 경험을 내보낸 것이다.
> - `[원문 확인]` 원본 자료에서 확인한 경험 · `[내가 입력]` 사용자가 직접 넣거나 고친 것 · `[확인 필요]` 근거를 원본에서 찾지 못해 사용자가 아직 확인하지 않은 것 — 확인된 사실처럼 쓰지 않는다.
> - 「근거」의 인용은 원본 발췌문이고, 「보완」은 사용자가 질문에 직접 한 답이다.
> - `(AI 해석)` 이 붙은 것(역량 · 문항 유형 · 추천 이유 · 요구사항 판정)은 AI 가 붙인 해석이지 원문 사실이 아니다.
> - 「팀」은 팀이 한 일, 「알 수 없음」은 누가 했는지 모르는 일이다 — 사용자 혼자 한 일처럼 바꿔 쓰지 않는다.
> - 여기 없는 경험 · 수치는 「없다」가 아니라 「쌓인 자료에 없다」이다. 지어내지 않는다.
```

- `scope` — `all` · `activity` · `application`. `id` — 활동 · 지원 ID, `all` 이면 `null`.
- 제목: 전체 `# 내 경험`, 활동은 활동 이름, 지원은 `# <지원처 이름> — 지원`(이름이 없으면 `# 이름 없는 지원`).
- 「읽는 법」은 세 대상 모두 같은 글이다(문장은 BE 가 다듬어도 되지만 뜻은 바꾸지 않는다 — `mcp-api.md` 「읽는 규칙」과 같은 뜻).

### 활동 블록 — 「전체」 · 「활동 하나」가 같이 쓴다

```markdown
## 바꿔요 — 캠퍼스 중고거래 앱

2025-03 ~ 2025-06 · 경험 2개

계기 [내가 입력]: 문제만 풀다 보니 직접 서비스를 만들어 보고 싶어졌다

### 채팅 메시지가 늦게 도착하는 문제를 폴링에서 WebSocket 으로 바꿔 해결했다

[원문 확인] · 수행: 나 · 역량 (AI 해석): 문제 해결, 기술 구현

근거
> 채팅 메시지가 늦게 도착하는 문제가 있었다. 내가 폴링을 WebSocket 으로 바꿔 해결했다.
>
> — 바꿔요-회고.md · 5줄

보완 [내가 입력]
- Q. 폴링을 WebSocket 으로 바꿀 때 직접 고친 부분은 어디였나요?
  A. 서버에 STOMP 엔드포인트를 만들고, 앱의 3초 폴링 코드를 구독 방식으로 바꿨다

### 백엔드 API 설계를 맡았다

[확인 필요] · 수행: 나 · 역량 (AI 해석): 기술 구현

근거
> 나는 백엔드 API 설계를 전부 맡았다.
>
> — 바꿔요-회고.md · 원본에서 찾지 못한 발췌
```

| 줄 | 규칙 |
| --- | --- |
| 활동 제목 | `##` (「활동 하나」에서는 문서 제목이 활동 이름이라 이 줄을 빼고 바로 기간 줄) |
| 기간 | `start ~ end`, 진행 중이면 `start ~ 진행 중`, `start` 가 `null` 이면 `기간 모름`. 원본에 있는 만큼만(README 「기간」) |
| 계기 | `note` 가 있을 때만. 늘 사용자가 쓴 것이라 `[내가 입력]` |
| 경험 제목 | `###` + 경험 `content`. 줄바꿈이 있으면 첫 줄을 제목으로, 나머지는 제목 아래 문단으로 |
| 상태 줄 | `[출처 상태]` · `수행: 나 / 팀 / 알 수 없음` · 역량. 역량이 `[]` 면 역량 칸을 뺀다. `competenciesBy: AI` 면 `역량 (AI 해석):`, `USER` 면 `역량:` |
| 외부 AI 가 고친 경험 | `mcpChange` 가 있으면 상태 줄 끝에 `· Claude 가 고침(확인 전)` — 본문은 지금 값, 상태는 이미 `[확인 필요]` |
| 내가 쓴 지원서에서 온 경험 | `origin` 이 있으면 상태 줄 다음에 `출처: 내가 쓴 지원서 · <지원처> · <문항>` |
| 근거 | `citations` 순서대로 인용 블록 하나씩. 출처 줄은 `— <sourceName> · <위치>`: `location.section` 이 있으면 `2쪽` · `2–3쪽` · `슬라이드 4`, 없고 줄 번호가 있으면 `5줄` · `5–7줄`, 둘 다 없으면 이름만. `matched: false` 면 위치 대신 `원본에서 찾지 못한 발췌`. 근거가 없으면 이 칸을 뺀다 |
| 보완 | `mcpChange` 가 **없는** 보완만, 만든 순서. 없으면 이 칸을 뺀다 |
| 순서 | 활동은 타임라인 순서(`GET /api/activities` — `period.start` 오름차순, `null` 맨 뒤), 경험은 활동 세부 순서 |
| 빈 활동 | 경험이 0개면 기간 줄 아래 `아직 경험이 없어요` 한 줄 |

### 「전체」

공통 머리(제목 `# 내 경험`) → 첫 줄 `활동 N개 · 경험 M개` → 활동 블록을 타임라인 순서대로, 블록 사이에 `---`.
빈 계정이면 `아직 쌓인 활동이 없어요` 한 줄로 끝난다(200).

### 「지원 하나」

```markdown
# OO 백엔드 부트캠프 — 지원

종류: 부트캠프 · 교육 과정 · 직무: 백엔드 · 서버 · 상태: 냈음 · 낸 달: 2026-11
공고: https://example.com/recruit/1234

## 문항 1. 기술적인 문제를 해결한 경험을 구체적으로 적어 주세요.

유형 (AI 해석): 문제 해결 · 기술적 어려움 · 목표 1000자

### 내가 쓴 답 — 확정 2026-11-06

「바꿔요」 프로젝트에서 채팅 메시지가 늦게 도착하는 문제가 있었고, …

### 이 문항이 보려는 것 (AI 해석)

- 기술 문제의 원인을 찾아 해결한 경험 — 근거 있음
- 해결한 뒤 결과를 확인한 방법 — 자료에서 확인 안 됨

### 고른 경험

#### 채팅 메시지가 늦게 도착하는 문제를 폴링에서 WebSocket 으로 바꿔 해결했다

활동: 바꿔요 — 캠퍼스 중고거래 앱 · [원문 확인] · 수행: 나

추천 이유 (AI 해석): 채팅 지연이라는 기술 문제를 직접 해결한 사례라 문항과 맞는다

근거
> …
```

| 칸 | 규칙 |
| --- | --- |
| 지원 줄 | 종류 · 직무 · 상태 · 낸 달 중 값이 있는 것만. 공고는 `postingUrl` 이 있을 때만 |
| 문항 | 지원서 순서대로 `## 문항 N. <text>`. 유형은 `questionTypeBy: AI` 면 `(AI 해석)`, 없으면 빼고, `targetLength` 가 있으면 `목표 N자` |
| 내가 쓴 답 | 확정 답(`answer.text`)이 있으면 `내가 쓴 답 — 확정 <YYYY-MM-DD>`. 없고 임시 글(`answerDraft.text`, 빈 글 아님)이 있으면 `쓰는 중인 글 — 확정 전`. 둘 다 없으면 `아직 쓴 답이 없어요` |
| 보려는 것 | `requirements` 그대로, 판정은 `근거 있음` · `일부` · `자료에서 확인 안 됨`. 0개면 칸을 뺀다 |
| 고른 경험 | `recommendations` 순서대로 경험 블록(위 「활동 블록」의 경험과 같은 모양 — 제목만 `####`) + `활동:` · `추천 이유 (AI 해석):`. `emphasis` · `gaps` 는 싣지 않는다 |
| 분석 중 · 실패 문항 | `status` 가 `ANALYZING` 이면 `추천을 찾는 중이에요 — 끝난 뒤 다시 내보내 주세요`, `FAILED` 면 `추천을 찾지 못했어요(<error.code>)`. 보려는 것 · 고른 경험 칸을 빼고 답 칸은 그대로. 추천을 대신 채우지 않는다(대회 규칙 2) |

### 값 → 글자

README 「값 목록」의 「뜻」 칸을 쓴다 — `—` 뒤의 설명은 뺀다(예: `NOT_PASSED` → `불합격`, `JOB` → `채용(신입 · 경력)`).
출처 상태는 `원문 확인` · `내가 입력` · `확인 필요`, 수행 주체는 `나` · `팀` · `알 수 없음`, 지원 상태는 `작성 중` · `냈음` · `합격` · `불합격` · `모름`.

### 글 안의 특수 문자

사용자 글(경험 본문 · 발췌 · 보완 · 답)은 **고치지 않는다**. Markdown 구조가 깨지지 않게만:

- 인용 블록 안의 글은 줄마다 앞에 `> ` 를 붙인다.
- 제목으로 쓰는 경험 본문 · 문항 글 맨 앞의 `#` 은 `\#` 로 바꾼다.
- 그 밖의 Markdown · HTML 기호는 그대로 둔다(파일은 우리 화면에서 그리지 않는다 — 받는 도구의 몫).

## 싣지 않는 것 — 정한 이유와 함께

| 무엇 | 싣나 | 이유 |
| --- | --- | --- |
| 확인 전 「Claude 를 거친 답」(보완 `mcpChange` 있음) | **안 싣는다** | SPEC S-56 — 사용자가 맞아요를 누르기 전엔 「내가 입력」이 아니다 |
| 외부 AI 가 고친 경험 본문(경험 `mcpChange` 있음) | 싣는다 · `Claude 가 고침(확인 전)` 꼬리표 | 지금 본문이 그것이라 빼면 경험이 사라진다. 상태가 이미 `[확인 필요]` 다 |
| 활동 계기(`note`) | **싣는다** · `[내가 입력]` | 사용자가 직접 쓴 한 줄이라 들고 나갈 데이터다. experience-api 「이 계약에 없는 것」의 해당 줄을 이 계약으로 고친다 |
| 이어짐(`links`) | 안 싣는다 | 문장(`reason`)이 AI 해석이고, 확인한 이어짐도 두 활동 이름 말고는 담을 게 적다. 제출 뒤 필요하면 `CONFIRMED` 만 |
| 공개 프로필 표시(`shared`) · 저장(`saved`) | 안 싣는다 | 앱 안의 설정이지 경험 내용이 아니다 |
| 활동 분류(`category`) | 안 싣는다 | 화면 정리용 — experience-api 결정 그대로(MCP 에도 없다) |
| 쓰인 지원(`usedIn`) | 안 싣는다 | 지원 내보내기가 같은 정보를 반대 방향으로 담는다 |
| 같은 활동 제안(`mergeSuggestion`) | 안 싣는다 | 사용자가 정할 AI 제안이다 |
| AI 답변 초안(`draft`) · 새 경험 후보 · 되묻기(답 안 한 것) · 근거 점검 결과 | 안 싣는다 | 사용자가 확정하지 않은 AI 산출물이다. 사용자가 답칸에 넣은 글은 「내가 쓴 답 · 쓰는 중인 글」로 나간다 |
| 추천의 `emphasis` · `gaps` | 안 싣는다 | 문항을 쓰는 동안의 작업 도움말이다. 추천 이유 하나만 해석으로 싣는다 |
| 원본 자료 전문 | 안 싣는다 | 근거 발췌와 원본 이름이 실린다(MCP 와 같다). 원본 다운로드는 자료 빼기(ETC#180)와 같이 본다 |

## 다른 사용자의 데이터

- 세션 주인 것만 읽는다. 남의 `activityId` · `applicationId` 는 없는 것과 똑같이 404(있는지조차 드러내지 않는다).
- 「전체」는 세션 주인의 활동만.

## FE 가 할 것 (FE#149)

- `fetch(…, { credentials: 'include' })` → `response.ok` 면 `blob()` 을 받아 `<a download>` 로 내려받는다. 파일 이름은 `Content-Disposition` 의 `filename*` 을 먼저, 없으면 ASCII 규칙.
- 실패하면 오류 · 다시 시도(같은 호출). 지어낸 파일로 대신 내려주지 않는다(대회 규칙 2).
- 목 모드는 지어낸 파일을 진짜처럼 내려주지 않는다 — 「실제 서버에서만 내보낼 수 있어요」처럼 안 되는 이유를 보이거나, 쓴다면 `MOCK(<id>):` + ETC `ai-scope.md` §3.

## 이 계약에 없는 것

- PDF · DOCX · JSON · 고른 일부만 내보내기(ETC#31)
- 활동마다 파일을 나눈 `.zip`
- MCP 도구로 내보내기 — 외부 AI 는 이미 `get_activity` · `search_experiences` 로 같은 데이터를 읽는다
- 내보낸 파일을 다시 가져오기(ETC#96 「다른 AI 에서 가져오기」와 같이 본다)
