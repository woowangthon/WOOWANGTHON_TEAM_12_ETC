# ADR-002: 스프린트 반복 — 흐름 하나를 끝까지 잇고, 화면을 보며 고친다

- 상태: 채택 — 「다음 스프린트 기능을 미리 만들지 않는다」만 대체됨 → ADR-009
- 날짜: 2026-11-02

## 배경

- 기획의 큰 그림은 Notion 「기획 다듬기」(c337 기획 논의 통합 기록)에 있다. 하지만 화면 배치 · 정보의 양 · 사용 흐름은 PM 이 실제 화면을 써 봐야 판단할 수 있다.
- 제출까지 2주가 안 된다(11-15). 팀은 프론트 · 디자인 셋, 백엔드 · 클라우드 하나, PM 하나다.
- 지난 팀 프로젝트(이어봄)는 요구사항 · 기획 문서를 두껍게 맞추느라 시간을 쓰다 AI 와 완성도가 줄었다(본선 탈락).
- 심사의 「구현 완성도 25」는 기능 수보다 처음부터 끝까지 매끄럽게 이어지는 흐름에서 나온다.

## 결정

- **스프린트 하나 = 사용자 흐름 하나.** 우선순위(`P0` 부터) 순서로 고르고, 모든 레포에 같은 이름의 Milestone(`스프린트 N — <흐름>`)을 둔다. **기간은 정하지 않는다** — 목표 흐름이 데모처럼 돌면 닫고 다음으로 간다.
- **SPEC 은 스프린트를 시작할 때 그 스프린트 몫만 채운다.** Notion 기획을 초안으로 삼아 옮긴다. 다음 스프린트 기능을 미리 SPEC · 코드에 만들지 않는다.
- **흐름 하나를 화면부터 DB · AI 까지 먼저 잇는다.** 레포마다 따로 완성한 뒤 합치지 않는다. 계약 전엔 목으로 시작한다.
- **고정할 것과 바꿔도 되는 것을 나눈다.**

  | 고정 — SPEC · 계약으로 관리, 바꾸려면 묻는다 | 바꿔도 됨 — 담당이 정하고 PR 에 스크린샷 |
  | --- | --- |
  | 경험을 쌓고 다른 목적에 다시 쓴다는 목적 | 화면 배치 · 메뉴 · 탭 · 페이지 수 |
  | 원본 근거를 보존한다 | 카드 모양 · 입력 폼 구성 |
  | 원문에서 확인한 것 · 사용자가 말한 것 · AI 추측을 구분한다 | 문구 · 색 · 스타일 · 애니메이션 |
  | 레포 사이 데이터의 의미(계약) | 레포 안 구현 방식 |

- **이슈 담당은 미리 정하지 않는다.** 논의는 영역 담당(프론트 · 디자인 · 백엔드 · 기획)과 Notion · DM 으로 하고, 구현은 시간이나 AI 에이전트 토큰이 있는 사람이 이슈를 가져가 시작할 때 자기를 담당으로 건다. 그래서 **이슈 본문만 읽고 누구의 에이전트든 시작할 수 있게** 의도 · SPEC 참조 · 완료 조건 · 읽을 것을 본문에 담는다. Notion 은 링크만 덧붙인다.
- **PM 은 화면을 보고 피드백한다.** UI 가 바뀌는 PR 에는 덜 된 화면이어도 스크린샷(또는 미리보기 링크)을 붙인다. 피드백은 「이번 스프린트에서 고침 / 다음 스프린트 / `P2`」 셋으로 나눠 이슈에 남긴다.

## 버린 안

- **전체 설계 후 개발** — 엔터티 · API · 화면을 먼저 다 확정하면 병렬 작업이 깔끔하다. 하지만 화면을 보기 전엔 판단할 수 없는 게 많아 다시 고치게 되고, 이어봄에서 이 방식으로 AI 쪽 시간이 줄었다.
- **레포별로 각자 완성한 뒤 통합** — 담당끼리 기다릴 일이 없다. 하지만 마지막에 붙이다 어긋나고, 실제로 도는 화면을 늦게 본다.
- **이슈마다 담당을 미리 배정** — 누가 무엇을 하는지 한눈에 보인다. 하지만 실제로는 그때 시간 · 토큰이 남는 사람이 하게 돼서 배정이 금방 틀어진다.
- **기간을 정한 스프린트(예: 3일)** — 진척을 재기 쉽다. 하지만 2주 남짓에 날짜 · 회고 의식을 얹는 비용이 이득보다 크다고 PM 이 판단했다.

## 결과

- PM 이 실제 화면을 빨리 보고 방향을 잡는다. 담당은 UI 세부를 묻느라 멈추지 않는다.
- SPEC 이 스프린트마다 늘어나서, 앞에서 정한 데이터 구조가 뒤 스프린트에서 바뀔 수 있다. 계약 변경은 머지 규칙 4(반대편 승인)로 묶는다.
- 기간이 없으니 한 스프린트가 늘어질 위험이 있다. PM 이 「흐름이 돌았나」로 닫을지 판단한다.
