# ADR-003: Spring Boot + FastAPI + PostgreSQL — AI 서버는 DB 없이 JSON 만 주고받는다

- 상태: 대체됨 → ADR-007 (「LangGraph 는 지금 쓰지 않는다 · AI 흐름은 함수로」 항목만. 나머지 — 스택 · AI 서버는 DB 를 만지지 않는다 · 내부망 — 는 유효)
- 날짜: 2026-11-02

## 배경

- 백엔드 · 클라우드 담당이 한 명이고, AI 서버는 PM 이 AI 에이전트로 맡는다. 두 사람이 서로 기다리지 않고 따로 일할 수 있는 경계가 필요하다.
- Notion 「기획 다듬기」 §9.2 에 스택 안이 있었지만(Spring Boot · FastAPI · PostgreSQL(+pgvector) · LangGraph) 팀 확정은 아니었다. BE 담당이 이 안으로 확정할지 물어 와서 이번에 정한다.
- 스프린트 1 의 AI 일(SPEC F-02)은 「추출 → 근거 원문 대조」 일자형이다. 문항 매칭 · 되묻기는 다음 스프린트다.

## 결정

- **BE: Spring Boot**(인증 · 데이터 · 작업 상태). **AI: Python FastAPI**. **DB: PostgreSQL** 하나.
- **AI 서버는 DB 를 만지지 않는다.** BE 가 원본 텍스트(나중엔 후보 경험)를 보내면 AI 서버는 결과 JSON 만 돌려준다. 저장 · 사용자 구분 · 호출 횟수는 BE 가 맡는다. 계약은 ETC `docs/contracts/ai-api.md` 하나(ETC#6).
- **AI 서버는 밖에 공개하지 않는다.** BE 만 내부망으로 부른다([ADR-004](ADR-004-deploy.md)). LLM 키는 AI 서버에만 둔다.
- **pgvector · LangGraph 는 지금 쓰지 않는다.**
  - 매칭은 사용자 한 명의 경험(수십 ~ 백여 개)을 LLM 에 후보로 넘기는 것으로 시작한다. DB 이미지는 `pgvector/pgvector` 로 받아 둬서, 검색이 실제로 느려지거나 후보가 넘치면 확장만 켠다.
  - AI 흐름은 함수 몇 개로 잇는다. 되묻기 반복처럼 분기 · 상태가 생기면 그때 LangGraph 를 검토한다.
- LLM 모델은 아직 미정이다(SPEC 미결정 질문 4).

## 버린 안

- **BE 하나(Spring)에서 LLM 까지 호출** — 서버가 하나라 배포 · 계약이 단순하다. 하지만 AI 담당과 BE 담당이 같은 코드에서 부딪치고, 파이썬 쪽 LLM · 문서 파싱 도구를 못 쓴다.
- **AI 서버가 DB 를 직접 읽고 쓰기** — 매칭 때 BE 를 거치지 않아 빠르다. 하지만 스키마를 두 레포가 같이 알아야 해서 바꿀 때마다 둘 다 고치고, 사용자 데이터 접근 경로가 둘이 된다.
- **처음부터 pgvector 임베딩 검색 · LangGraph 다중 에이전트** — 기획 그림엔 맞다. 하지만 지금 데이터 크기와 2주 일정에선 얻는 게 없고 설정 · 디버깅 비용만 는다.

## 결과

- 두 레포가 계약 JSON 하나로 병렬 작업한다. AI 서버는 상태가 없어 테스트 · 재시작이 쉽다.
- 매칭 때 BE 가 후보 경험을 실어 보내야 해서 요청이 커진다. 너무 커지면 pgvector 로 후보를 먼저 줄인다.
- 결정은 스프린트를 돌며 바뀔 수 있다. 바뀌면 이 ADR 을 고치지 않고 새로 쓴다.
