# ADR-006: SPEC · 계약 PR 은 승인 대신 알림 — 머지 규칙 4 를 바꾼다

- 상태: 채택
- 날짜: 2026-11-02

## 배경

- ADR-001 은 「SPEC · 계약을 바꾸는 PR 만 반대편 담당 승인」을 남겼다. 레포 사이를 깨는 변경을 막으려는 것이었다.
- 실제로는 다 된 PR 이 승인 대기로 멈췄다. ETC#18 이 그랬다(S-11 P0 + 추가 · 삭제 API). 팀원은 각자 시간 · 토큰이 날 때 일해서(ADR-002), 승인이 며칠씩 걸릴 수 있다.
- 각 레포의 일은 에이전트가 이슈를 가져갈 때 SPEC · 계약을 **그때 다시 읽고** 시작한다(공통 규칙 「시작 전에 읽는다」). 바뀐 계약은 다음 시작부터 자연히 반영된다.
- 승인이 실제로 막아 주던 위험은 하나다. **이미 만들고 있는 사람이 모르는 사이** 계약이 바뀌는 것. 이건 알림으로 막을 수 있다.

## 결정

- 머지 규칙 4: SPEC · `docs/contracts/` 를 바꾸는 PR 은 **승인 없이 머지한다.** 대신 머지 전에 **영향받는 레포의 열린 이슈에 「무엇이 바뀌었나 한 줄 + PR 링크」 댓글을 단다.** 진행 중(담당이 걸린) 이슈면 그 담당을 부른다.
- 자율 경계: 계약 변경을 「먼저 묻는다」에서 「그냥 한다(알림)」로 옮긴다. 다른 레포 **코드**와 남이 담당한 이슈는 그대로 「먼저 묻는다」.
- 반영할 곳: `AGENTS.md` 공통 블록 · ETC 「이 레포」, `README.md`, `docs/SPEC.md` 머리말, `docs/contracts/README.md`, PR 템플릿, `implement-issue` · `sync-spec` 스킬. 공통 블록 · 스킬 · 템플릿은 `scripts/sync-shared.sh` 로 FE · BE · AI 에 복사한다.
- ADR-002 「결과」의 「계약 변경은 머지 규칙 4(반대편 승인)로 묶는다」는 이 ADR 로 대체된다(옛 ADR 은 고치지 않는다).

## 버린 안

- **승인 유지** — 반대편이 반드시 읽는다. 하지만 2주 남짓에 대기로 막히는 비용이 크고, 에이전트가 시작 때 다시 읽으니 얻는 게 작다.
- **규칙 자체를 없앰(알림도 없이)** — 가장 빠르다. 하지만 이미 구현 중인 사람이 바뀐 걸 모르고 옛 계약대로 끝낼 수 있다. 댓글 한 줄이면 막히는 위험이라 남겼다.

## 결과

- 계약 · SPEC 변경이 바로 main 에 들어가고, 다른 레포는 다음 작업부터 따른다.
- 남은 위험: 알림을 못 본 채 옛 계약으로 PR 을 낼 수 있다. 각 레포의 implement-issue 는 PR 전에 계약을 다시 읽는다(검증 단계).
